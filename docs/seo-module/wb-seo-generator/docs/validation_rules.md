# Validation Rules — спецификация валидатора

Валидатор — программный модуль, который проверяет выход LLM на соответствие жёстким правилам SEO **до** записи результата. Если валидация не прошла, запускается retry с обратной связью для LLM.

Этот документ — исчерпывающая спецификация проверок. Codex реализует каждую проверку как отдельную функцию в `validation/checks.py` с сигнатурой `def check_X(card: GeneratedCard, brief: Brief) -> CheckResult`.

---

## Типы результатов

```python
from enum import Enum
from pydantic import BaseModel


class Severity(str, Enum):
    ERROR = "error"      # блокирует принятие, требует retry
    WARNING = "warning"  # не блокирует, но логируется


class CheckResult(BaseModel):
    check_name: str
    passed: bool
    severity: Severity
    message: str | None = None
    details: dict | None = None


class ValidationReport(BaseModel):
    results: list[CheckResult]

    @property
    def failed(self) -> bool:
        return any(not r.passed and r.severity == Severity.ERROR for r in self.results)

    @property
    def error_messages(self) -> list[str]:
        return [r.message for r in self.results if not r.passed and r.severity == Severity.ERROR]
```

## Категория 1 — Формат и структура (ERROR)

### 1.1. Длина названия
**Проверка:** `len(card.title) <= 60`
**Сообщение при провале:** `"Название {N} символов, должно быть ≤ 60"`

### 1.2. Длина описания
**Проверка:** `len(card.description) <= 5000`
**Сообщение при провале:** `"Описание {N} символов, должно быть ≤ 5000"`

### 1.3. Количество характеристик
**Проверка:** `len(card.characteristics) >= 8`
**Сообщение при провале:** `"Заполнено {N} характеристик, минимум 8"`

### 1.4. Шесть блоков в описании
**Проверка:** `len(card.description_blocks()) == 6`
**Сообщение при провале:** `"Описание содержит {N} блоков, должно быть 6 (разделены пустой строкой)"`

### 1.5. Уникальность полей характеристик
**Проверка:** нет дублей в `[c.field for c in card.characteristics]`
**Сообщение при провале:** `"Дублирующиеся поля характеристик: {list}"`

## Категория 2 — Запреты в названии (ERROR)

### 2.1. Запрещённые символы в названии
**Регекс:** `r"[/⭐★♥✓❤🔥💎!]|[A-ZА-Я]{4,}"` (CAPS ≥ 4 букв подряд)
**Сообщение:** `"В названии найдены запрещённые символы: {matches}"`

### 2.2. Запрещённые слова в названии
**Стоп-лист (case-insensitive, проверка по словам):**
```python
TITLE_STOP_WORDS = {
    "купить", "цена", "стоимость",
    "скидка", "распродажа", "акция",
    "лучший", "лучшая", "лучшее", "лучшие",
    "идеальный", "идеальная", "идеальное",
    "элегантный", "элегантная", "элегантное",
    "премиальный", "премиальная", "премиальное",
    "уникальный", "уникальная", "уникальное",
    "шикарный", "шикарная", "шикарное",
    "качественный", "качественная",  # без подтверждающей конкретики
}
```
**Сообщение:** `"В названии запрещённые слова: {found}"`

### 2.3. Повтор слов в названии
**Проверка:** нет слова (длиннее 3 букв, приведённого к нижнему регистру и лемматизированного простым способом — обрезание окончания) встречающегося больше 1 раза
**Сообщение:** `"В названии повторяется слово: {word}"`

### 2.4. Эмодзи в названии
**Проверка:** не содержит Unicode emoji (`\U0001F600-\U0001F64F`, `\U0001F300-\U0001F5FF`, etc.)
**Сообщение:** `"В названии найдены эмодзи"`

## Категория 3 — Переспам по ключам (ERROR)

### 3.1. Каждый ключ ≤ 3 раз во всей карточке
**Алгоритм:**
1. Собрать все ключи из брифа: `brief.semantika.vch + brief.semantika.sch + brief.semantika.nch + brief.semantika.okolo`
2. Для каждого ключа нормализовать (привести к нижнему регистру, убрать знаки препинания)
3. Подсчитать количество вхождений в `card.all_text()` (также нормализованном)
4. Вхождения считать по нормализованному тексту + как подстроку (для многословных ключей) + по совпадению начальной формы первых 5 букв каждого слова (для учёта словоформ)

**Проверка:** все ключи встречаются `<= 3` раза
**Сообщение:** `"Ключ '{key}' встречается {N} раз (лимит 3)"`

### 3.2. Главный ВЧ-ключ ≤ 2 раз в описании
**Проверка:** первый элемент `brief.semantika.vch` встречается в `card.description` не более 2 раз
**Сообщение:** `"Главный ВЧ-ключ '{key}' в описании {N} раз (лимит 2)"`

### 3.3. Главный ВЧ-ключ в первых 3 словах названия
**Проверка:** первый элемент `brief.semantika.vch` содержится в первых 3 словах `card.title` (по нормализованной форме)
**Сообщение:** `"Главный ВЧ-ключ '{key}' не в первых 3 словах названия"`

---

## Категория 4 — Антиспам между полями (ERROR)

### 4.1. Перечисление через запятую в полях характеристик
**Проверка:** ни в одном значении характеристики нет более 4 фрагментов, разделённых запятыми
**Исключение:** поля «Комплектация», «Особенности модели», «Назначение», «Повод» — допускают перечисления до 5 элементов
**Сообщение:** `"Характеристика '{field}' содержит перечисление из {N} элементов (похоже на спам)"`

### 4.2. Дубли слов между полями
**Алгоритм:**
1. Собрать все значимые слова (длиннее 4 букв, исключая стоп-слова языка) из каждого поля характеристик
2. Найти слова, встречающиеся в 3+ разных полях
3. Исключить слова, соответствующие значениям обязательных фильтров (цвет, размер, пол)

**Проверка:** таких слов нет (кроме фильтруемых)
**Сообщение:** `"Слово '{word}' повторяется в {N} полях характеристик"`

### 4.3. Близкие вариации одного слова
**Алгоритм:**
1. Извлечь все слова длиннее 5 букв из названия и характеристик
2. Попарно сравнить — если первые 5 букв совпадают и слова не идентичны, это вариация
3. Допустимы вариации из стоп-листа исключений (мужчина/мужской — разные формы, не спам)

**Проверка:** нет пар близких вариаций в одном поле
**Сообщение:** `"Близкие вариации в поле '{field}': {word1} и {word2}"`

## Категория 5 — Человечность (WARNING)

Эти проверки не блокируют принятие (текст может быть формально корректен), но логируются для аналитики качества промпта.

### 5.1. Оценочные прилагательные без конкретики
**Стоп-лист:** `["высокое качество", "долговечный", "удобный", "стильный", "подходит всем", "эргономичный", "комфортный", "надёжный"]`
**Проверка:** если такое прилагательное найдено, проверить наличие в пределах 20 слов конкретики (чисел, размерностей, материалов)
**Severity:** WARNING
**Сообщение:** `"Оценочное '{phrase}' без конкретики в пределах 20 слов"`

### 5.2. Обращения-канцеляризмы
**Стоп-лист:** `["дорогой покупатель", "уважаемые клиенты", "дорогие покупатели", "уважаемый покупатель"]`
**Severity:** ERROR
**Сообщение:** `"Найдено обращение-канцеляризм: {phrase}"`

### 5.3. Восклицательные знаки в описании
**Проверка:** в описании ≤ 1 восклицательного знака
**Severity:** ERROR
**Сообщение:** `"В описании {N} восклицательных знаков (максимум 1)"`

### 5.4. Запрещённые продающие штампы
**Стоп-лист:** `["идеальный подарок", "лучший выбор", "не упустите шанс", "порадует вас", "восторг"]`
**Severity:** ERROR
**Сообщение:** `"Продающий штамп: {phrase}"`

### 5.5. Наличие конкретного сценария в первых 3 строках
**Проверка:** первый блок описания (до первой пустой строки) содержит хотя бы одно слово из `brief.stsenarii` или числовую конкретику
**Severity:** WARNING
**Сообщение:** `"В первом блоке описания нет конкретного сценария или цифр"`

### 5.6. Наличие блока «что не входит»
**Условие:** если `brief.ne_vhodit` не пустое
**Проверка:** в описании (в блоке 4) присутствует фраза «не входит» или «не входят» или перечисление того, что указано в `brief.ne_vhodit`
**Severity:** WARNING
**Сообщение:** `"Не упомянуто, что не входит в комплект: {items}"`

---

## Категория 6 — Релевантность отчёта (WARNING)

### 6.1. Охват кластеров ≥ 60% от общей семантики
**Проверка:** `card.report.coverage >= int(brief.semantika.total() * 0.6)`
**Severity:** WARNING
**Сообщение:** `"Низкий охват: {coverage} из {total} возможных кластеров"`

### 6.2. Использованные запросы действительно присутствуют в тексте
**Проверка:** каждый элемент `card.report.used_queries` встречается (целиком или через непрямое вхождение — разделённые слова) в `card.all_text()`
**Severity:** ERROR
**Сообщение:** `"Запрос '{query}' помечен как использованный, но не найден в тексте"`

## Retry-логика

### После первой неудачной валидации

Дополнение к user-сообщению для retry (через OpenRouter):

```
Предыдущая генерация не прошла валидацию. Ошибки:
- {error_1}
- {error_2}
...

Исправь ТОЛЬКО эти ошибки, сохрани всё остальное. Верни полный ответ в том же формате.
```

### После второй неудачной валидации

Переключение на fallback-модель (`anthropic/claude-sonnet-4.5`) с тем же промптом и перечнем ошибок.

### После третьей неудачной валидации

SKU помечается как `failed` со статусом `validation_failed` и списком не пройденных проверок. Обработка партии продолжается со следующего SKU.

---

## Метрики для логирования

По каждой партии логировать:

- Количество SKU обработано / провалено
- Средний охват кластеров по партии
- Топ-5 самых частых ошибок валидации
- Общая стоимость (по metadata OpenRouter)
- Процент SKU, потребовавших retry
- Распределение по моделям (Haiku vs Sonnet fallback)

Это поможет итеративно улучшать промпт по реальной статистике провалов.
