# AGENTS.md — WB SEO Generator

Этот документ — основная точка входа для агента Codex, работающего над сервисом массовой генерации SEO-текстов карточек Wildberries.

---

## Назначение сервиса

Сервис принимает на вход брифы по SKU (структурированные факты о товаре + семантическое ядро) и генерирует через LLM три текстовых блока карточки WB:

1. **Название** (≤ 60 символов)
2. **Значения характеристик** (включая доп. поля)
3. **Описание** (≤ 5000 знаков)

Целевой масштаб — партии по 50–500 SKU. Сервис должен быть устойчив к сбоям LLM, автоматически валидировать выход по жёстким правилам SEO 2026 и ретраить проваленные генерации.

## Стек и ключевые решения

- **Язык:** Python 3.11+
- **Зависимости:** `httpx` (async HTTP), `pydantic` v2 (валидация схем), `openpyxl` (Excel I/O), `tenacity` (ретраи), `loguru` (логи)
- **LLM-провайдер:** OpenRouter (единая точка доступа ко всем моделям)
- **Базовая модель по умолчанию:** `anthropic/claude-haiku-4.5` (баланс цены и качества на русском)
- **Fallback-модель:** `anthropic/claude-sonnet-4.5` (только если валидация Haiku провалилась 2 раза подряд)
- **Кэширование промпта:** использовать OpenRouter cache-control заголовки для системного промпта (экономия ~40%)

## Ключевые правила разработки

### 1. Промпт и правила — источник истины

Всё, что касается содержания SEO (правила, голоса, структура описания), живёт **только в `prompts/` и `docs/`**. В коде Python не должно быть ни одного хардкода SEO-правила. Если правило меняется — правится соответствующий `.md`, код не трогается.

Это критично, потому что:
- правила WB меняются несколько раз в год;
- правила удобно читать и ревьюить в маркдауне, а не в Python-константах;
- промпт можно обновить без деплоя кода.

### 2. Валидация выхода — обязательна

Каждый ответ LLM прогоняется через валидатор (`docs/validation_rules.md` — спецификация). Валидатор проверяет программно:

- длину названия (≤ 60 символов);
- длину описания (≤ 5000 знаков);
- количество повторений каждого ключа из брифа (≤ 3 в сумме по всем полям);
- отсутствие запрещённых символов в названии (слэши, эмодзи, звёздочки, CAPS);
- отсутствие стоп-слов («купить», «цена», «лучший», «идеальный», «элегантный» в названии);
- заполненность обязательных блоков описания (6 блоков по шаблону).

Если валидация не прошла — retry с дополнением к промпту «предыдущая генерация провалила такие-то проверки, исправь».

### 3. Входные данные — Excel/CSV + YAML-брифы

Рабочий формат — Excel-таблица, где одна строка = один SKU. Колонки соответствуют полям брифа из `prompts/brief_schema.md`. Агент должен поддерживать:

- чтение `input/briefs.xlsx` → парсинг в `Brief` pydantic-модели;
- запись результатов в `output/results.xlsx` с колонками «название», «описание», «характеристики (JSON)», «отчёт (JSON)», «статус», «ошибки».

### 4. Идемпотентность партий

Если партия упала на середине — повторный запуск должен продолжить с того SKU, на котором упал, а не перегенерировать всё заново. Используем колонку «статус» в выходной таблице как чекпоинт (`pending` / `ok` / `failed` / `validated`).

### 5. Бюджетный контроль

Каждый запрос к OpenRouter возвращает метаданные о стоимости. Агент должен:

- логировать стоимость каждого SKU;
- складывать суммарный бюджет партии;
- останавливать обработку и запрашивать подтверждение, если бюджет партии превысил оценочный в 1,5 раза.

## Pipeline генерации (эталонный)

```
1. load_briefs(input.xlsx) → List[Brief]
2. for brief in briefs:
     if brief.status == 'ok': skip
     prompt = build_prompt(system_prompt, brand_voice, brief)
     response = openrouter.generate(prompt, cache=True)
     parsed = parse_output(response)
     validation = validate(parsed, brief)
     if validation.failed:
         prompt += f"\nПрошлая попытка провалила: {validation.errors}"
         response = openrouter.generate(prompt, model=fallback_model)
         parsed = parse_output(response)
         validation = validate(parsed, brief)
     save_result(output.xlsx, brief.sku, parsed, validation)
3. generate_summary_report(output.xlsx)
```

## Что Codex должен прочитать перед кодированием

В таком порядке:

1. `prompts/system_prompt.md` — понять, что именно отправляется LLM;
2. `prompts/brief_schema.md` — структура входа;
3. `prompts/output_schema.md` — структура выхода и как её парсить;
4. `docs/validation_rules.md` — спецификация валидатора (это основная часть бизнес-логики);
5. `docs/seo_rules_reference.md` — читать только если нужно понять «почему так» (для ревью промпта);
6. `prompts/brand_voices.md` — как подключается выбранный голос бренда в промпт;
7. `examples/example_backpack.md` — эталонный пример для написания тестов.

## Конвенции кода

- **Форматирование:** `ruff format`
- **Линтер:** `ruff check --select E,F,I,N,UP,B,SIM`
- **Типизация:** строгая, `mypy --strict` на всех модулях, кроме `scripts/`
- **Тесты:** `pytest`, минимум покрытие 80% на валидаторе и парсере
- **Логирование:** `loguru`, формат структурированный JSON для прода, человекочитаемый для dev
- **Секреты:** `.env` файл, ключ OpenRouter в `OPENROUTER_API_KEY`
- **Не использовать:** `print()`, `requests` (только `httpx`), синхронные вызовы к OpenRouter (только `async`)

## Приоритеты реализации

Если Codex получает задачу без явного приоритета — порядок работ такой:

1. Pydantic-схемы `Brief` и `GeneratedCard` (по `prompts/brief_schema.md` и `prompts/output_schema.md`)
2. Парсер ответа LLM (текстовый блок → `GeneratedCard`)
3. Валидатор (реализация `docs/validation_rules.md`)
4. Клиент OpenRouter с prompt caching
5. Excel I/O
6. Pipeline orchestration с retry и чекпоинтами
7. Интеграционный тест на `examples/example_backpack.md`
8. CLI (`python -m wb_seo_generator run --input briefs.xlsx --output results.xlsx`)

## Что НЕ делать

- Не встраивать SEO-правила в Python-код
- Не парсить ответ LLM регулярками — использовать разделители `===== SECTION =====` из `output_schema.md`
- Не передавать весь каталог Wildberries в промпт — только бриф конкретного SKU
- Не запрашивать LLM о текущих правилах WB — они уже в системном промпте
- Не использовать OpenAI SDK напрямую — только OpenRouter через `httpx`
- Не логировать полные промпты в production (только хэши) — системный промпт стабильный, бриф уже есть в таблице
